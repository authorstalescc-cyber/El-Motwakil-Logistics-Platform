# الخطة 06 — الأداء والرصد

**الحالة:** in_progress — 06-A مكتملة، هدف الداشبورد في 06-B تحقق بعد ثلاث موجات، وبدأت 06-C، و06-D مفعلة

**الأولوية:** P1

**التقدير الأولي:** 3–4 أيام

**الاعتماد:** الخطة 00

## الهدف

تحسين زمن الاستجابة بناءً على قياس قابل للتكرار، لا على عدد أسطر أو تخمينات استاتيكية.

## نطاق التنفيذ

1. عداد استعلامات وزمن DB وزمن الطلب وسجل بطيء في بيئة التطوير فقط، بلا أسرار أو قيم حساسة.
2. fixture أو نسخة بيانات منزوعة الحساسية بأحجام موثقة للمقارنة.
3. خفض الداشبورد من خط 77 استعلامًا، وتحميل التفاصيل الثقيلة عند الطلب.
4. تجميع badges التنقل في استعلام واحد مخزن مؤقتًا، لا استعلامًا لكل عنصر.
5. استبدال fuzzy scan على 21 حقلًا بمصدر أسماء مطبع ومفهرس أو استراتيجية bounded candidates.
6. معالجة `UNION` المصروفات والعد المنفصل والاستعلامات المترابطة وصفحات بلا pagination.
7. `EXPLAIN` قبل إضافة أي فهرس، مع قياس الكتابة والحجم بعده.
8. ميزانية أداء لكل صفحة حرجة وربطها بحزمة الاختبارات.

## حزم التنفيذ الصغيرة

### 06-A — القياس الآمن

- **الحالة:** مكتملة.
- إضافة instrumentation اختياري في التطوير مع redaction للمعرّفات والقيم المالية.
- تثبيت fixture بأحجام صغيرة/متوسطة/كبيرة وتسجيل نسخة PHP/DB والـcommit.
- الناتج: تقرير baseline قابل لإعادة التشغيل؛ لا يُفعل في الإنتاج افتراضيًا.
- أضيف `App\Core\Performance`: لا يعمل إلا مع `ALMOTAWAKEL_PERF=1` ومن CLI/الخادم المحلي وعلى قاعدة `almotawakel_test_*`. يسجل المسار بلا query string وبعد إخفاء المعرفات، وعدد الاستعلامات وزمن DB والطلب والحجم والذاكرة، والاستعلام البطيء كنوع وبصمة hash فقط بلا SQL أو parameters.
- أضيفت spans ثابتة للداشبورد لتوزيع الكلفة على أجزائه بلا تسجيل مدخلات مستخدم، وفاحص `verify_performance_foundation.php` يثبت الحارس وredaction.
- أضيف `bin/measure_performance_ui.py` لقياس خمس صفحات من Chromium وتوثيق أحجام fixture والإصدارات والـcommit. التقرير: [`2026-07-20-performance-baseline.md`](../../reports/2026-07-20-performance-baseline.md).
- أضيف `bin/seed_performance_fixture.php` بعينات حتمية مجهلة `small|medium|large` وحراس CLI/اسم القاعدة/التأكيد/خلو بيانات الأعمال، بلا أي حذف أو تعديل لصف قائم.

### 06-B — الداشبورد والتنقل

- **الحالة:** ثلاث موجات مكتملة؛ هدف الداشبورد ≤20 تحقق، وقياس badges التنقل المستقل متبقٍ.
- قياس كل استعلام قبل الدمج، ثم تجميع العدادات أو تأجيلها عند الطلب.
- مقارنة النتائج والعدّادات قبل/بعد، مع اختبار صلاحيات وعدم تسريب بيانات.
- رجوع: feature flag يعيد الاستعلامات السابقة دون تغيير النتائج.
- أزيلت إعادات حساب رصيد الخزنة وfeed اليوم وإجمالي عهدة المناديب، وجُمعت عدادات الداشبورد وملخص الأذونات وقائمتا lookup. انخفض الداشبورد من `78` إلى `55` استعلامًا على التثبيت الفارغ، وإلى `56` على fixture صغير؛ اجتازت الرحلات 5/5 وفاحصات التقفيل/العهدة/التزامن.
- على fixture المتوسط دُمج مخطط النشاط `5→1` وتقرير المصروفات `6→1`، وخُفض الداشبورد إلى `46` استعلامًا. نُقلت خيارات الإدخال السريع الثقيلة للتحميل عند فتح الأداة، وحُذف تكرار تفاصيل البطاقات المخفية مع بقاء مسارات الوصول الكاملة. هبط HTML من `826,784` إلى `188,873` بايت ونجحت الميزانيات.
- في الموجة الثالثة دُمج رصيد الخزنة `10→2`، وملخص اليوم `5→1`، وتفصيل يوم العهدة `3→1`، ولوحة المناديب `9→2` بعد تهيئة المخطط. دُمجت قائمة/ملخص الجاهز للفوترة وتصنيفات الحاويات، ونُقلت كل الخيارات الثانوية للإدخال السريع إلى التحميل الكسول. النتيجة `46→20` استعلامًا مع بصمة مالية متطابقة قبل/بعد.

### 06-C — البحث والصفحات الثقيلة

- **الحالة:** بدأت؛ ترقيم الأذونات مكتمل، والبحث الضبابي وبقية الصفحات متبقية.
- قياس المرشحين والذاكرة والزمن للبحث الضبابي، ثم تطبيق bounded candidates أو فهرس مطبع.
- إضافة pagination للصفحات التي يثبت القياس أنها ثقيلة؛ لا تغيير لترتيب النتائج دون قرار.
- بوابة: تطابق النتائج، ≤250ms للاستعلام الحرج على fixture، وعدم تجاوز حد المرشحين.
- أضيفت pagination خادمية لمتابعة الأذونات (48 بطاقة) ولسجلها (60 صفًا). البحث والتصفية والترتيب في المتابعة تعمل على كامل البيانات، والواجهة تصرح بأن إجماليات الجدول تخص الصفحة. هبط HTML `/permits` المتوسط من `988,298` إلى `189,646` بايت.

### 06-D — ميزانيات مستمرة

- تعريف p95 وعدد الاستعلامات وحجم HTML لكل رحلة حرجة.
- إضافة smoke performance إلى الخطة 08 ومراجعة الانحراف في كل إطلاق.
- **الحالة:** بوابة أولية منفذة ومشددة بعد بلوغ هدف الداشبورد. `run_browser_suite.py --performance` يشغل القياس تحت نفس حارس الخادم، وCI يرفض تجاوز `20/8/8/8/40` للصفحات الخمس، أو HTML 200KB، أو وجود استعلام يتجاوز 250ms.
- يتحقق القياس كذلك من endpoint خيارات الإدخال عند الطلب، سقف رسم 120 نتيجة في منتقي الإذن، وسقف 48 بطاقة لصفحة المتابعة، ثم يجرب بحثًا خادميًا حقيقيًا إن وُجد إذن مفتوح.

## أهداف أولية قابلة للمراجعة بعد fixture

- الداشبورد: ≤20 استعلامًا.
- البحث الضبابي: ≤5 استعلامات و≤2,000 مرشح في الطلب.
- لا استعلام يتجاوز 250ms على fixture القياسي.
- زمن p95 للرحلات المقاسة لا يزيد بعد تغييرات UX.
