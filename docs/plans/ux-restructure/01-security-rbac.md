# الخطة 01 — التحصين والصلاحيات

**الحالة:** complete

**الأولوية:** P0

**التقدير الأولي:** 2–3 أيام

**الاعتماد:** الخطة 00

## الهدف

إبقاء طريقة تشغيل البرنامج والنفق كما هي وفق قرار المالك، مع إضافة ضوابط تعويضية مناسبة لأن مكتب الإدارة متاح من الإنترنت.

## نطاق التنفيذ

1. إضافة قفل مؤقت ومعدل محاولات وتسجيل فشل دخول المكتب، من دون كشف وجود اسم المستخدم.
2. رفع الحد الأدنى لكلمات المرور الجديدة والمتغيرة، مع عدم تعطيل الحسابات القديمة قبل مسار ترقية واضح.
3. ضبط الجلسة: `HttpOnly` و`SameSite` وstrict mode ومهلة خمول، و`Secure` عندما يكون الطلب الخارجي HTTPS عبر proxy موثوق.
4. صفحة خطأ عامة وlogging داخلي، ومنع عرض SQL أو المسار المطلق أو stack trace للزائر.
5. إضافة CSRF وحارس المصادقة لمسار خروج المكتب.
6. تطبيق الأدوار: مالك، مدير، محاسب، تشغيل، قراءة فقط، عبر route/action policy مركزية بدل الحراس اليدوية المتفرقة.
7. حصر النسخ الاحتياطي والمستخدمين ومفاتيح AI في المالك، وعدم إعادة المفتاح الكامل إلى HTML بعد حفظه.
8. توحيد رفع المرفقات والتحقق من MIME والحجم والاسم، ثم تقديم الملف عبر endpoint مصرح بدل رابط عام مباشر.
9. إضافة security headers مناسبة مع اختبار عدم كسر الطباعة والتتبع والنفق.

| المستخدمون والمفاتيح والنسخ الاحتياطي | نعم | لا | لا | لا | لا |

المصفوفة تفصيل مبدئي؛ كل action سيملك صلاحية صريحة قبل التنفيذ.

## بوابة القبول

- اختبارات سماح ومنع لكل دور ولكل عملية حساسة.
- القفل يعمل تحت محاولات متزامنة ولا يقفل جميع المستخدمين بعنوان IP مشترك.
- لا يظهر سر محفوظ أو خطأ داخلي أو مرفق خاص لغير المصرح.
- لا تنكسر جلسات `/m` أو `/t` أو الطباعة أو العمل عبر النفق.
- توجد طريقة رجوع تلغي RBAC الجديدة دون فقد بيانات المستخدمين.

## نتيجة التنفيذ — 2026-07-19

- أضيفت سياسة مركزية في الراوتر للأدوار الخمسة، مع حراس إضافية للمستخدمين ومفاتيح AI والنسخ الاحتياطي.
- طُبق v40: أول حساب قائم `owner` والحسابان الآخران `manager`، مع جدول محاولات دخول لا يخزن username أو IP خامًا.
- فُعل قفل الحساب بعد خمس محاولات، وحد IP للفشل مع السماح لكلمة سر صحيحة من مستخدم آخر على شبكة مشتركة.
- فُعلت `HttpOnly` و`SameSite=Lax` وstrict mode ومهلة خمول؛ `Secure` وHSTS يعملان عند HTTPS القادم من cloudflared المحلي، ويبقى LAN/HTTP عاملًا.
- أضيفت صفحة 500 عامة برقم مرجع وlogging داخلي، وأزيل `X-Powered-By` وأضيفت رؤوس الحماية.
- مفاتيح AI لا تعود داخل قيمة HTML؛ الفراغ يبقي المفتاح، والحذف يحتاج اختيارًا صريحًا.
- المرفقات الجديدة تخزن في `storage/private_uploads`، والقديمة لا تخدم مباشرة من `/uploads`، والعرض يمر بكنترولر مصرح.
- النسخ الاحتياطي لا يضع كلمة مرور MySQL في سطر أوامر العملية.

### دليل البوابة

- `php bin/migrate_v40.php` نجح مرتين، ثم `php bin/verify_v40.php` نجح.
- 230 ملف PHP اجتازت `php -l`.
- 17 سكربت `verify_*.php` اجتازت الحزمة كاملة.
- Playwright اختبر الأدوار الخمسة، إظهار/إخفاء الأسرار، منع/سماح العمليات، إنشاء مستخدم بدور صريح، `/m/login` و`/t/{token}` والطباعة، بلا أخطاء console غير متوقعة.
- ثماني محاولات متزامنة قفلت حساب الاختبار، ومستخدم صحيح من IP المشترك ظل قادرًا على الدخول.
- HTTP أثبت غياب `X-Powered-By` ووجود رؤوس الحماية، وظهور `Secure` وHSTS عند محاكاة HTTPS.
- كل مستخدمي الاختبار المؤقتين حُذفوا؛ العدد المتبقي صفر.

### الرجوع

- نسخة ما قبل v40 محفوظة خارج المستودع، وchecksum سُجل في تقرير التنفيذ.
- يمكن تعطيل enforcement مركزيًا بإرجاع استدعاء `Access::enforce`، ثم إزالة أعمدة/جدول v40 في نافذة مستقلة إذا لزم؛ لا يتطلب الرجوع حذف المستخدمين.
