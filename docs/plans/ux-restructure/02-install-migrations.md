# الخطة 02 — التثبيت والترحيلات والاستعادة

**الحالة:** complete — 2026-07-19

**الأولوية:** P0

**التقدير الأولي:** 2–3 أيام

**الاعتماد:** الخطة 00

## الهدف

منع أي تشغيل اعتيادي للمثبت من مسح بيانات أو استيراد بيانات قديمة، وجعل الفشل صريحًا وقابلًا للاستعادة.

## نطاق التنفيذ

1. فصل أوضاع `install` و`update` و`import-legacy` بأوامر وخيارات مستقلة.
2. منع مسح البيانات واستيراد `old_data.json` إلا مع `--fresh --import-legacy` وتأكيد صريح. استُخدم `DELETE` داخل transaction بدل `TRUNCATE` حتى يبقى الرجوع ممكنًا وتُحترم المفاتيح الأجنبية.
3. تحليل رقم الترحيل من كل أسماء الملفات الحالية بصورة صحيحة، خصوصًا v30، ورفض الاسم غير المطابق بدل اعتباره v0.
4. fail-fast عند أول ترحيل فاشل، مع exit code غير صفري وعدم طباعة رسالة اكتمال.
5. جدول migration ledger يسجل الإصدار والوقت وchecksum والنتيجة.
6. وضعي `--dry-run` و`--verify-only`، وفحص prerequisites قبل أي كتابة.
7. نسخة احتياطية واختبار استعادة على قاعدة معزولة قبل اعتماد مسار التحديث.
8. تشغيل update مرتين لإثبات idempotency، واختبار فشل مصطنع في المنتصف.

## خارج النطاق

- تغيير معنى البيانات القديمة أو صيغ الحسابات.
- تشغيل الترحيلات الجديدة على قاعدة الإنتاج ضمن هذه الخطة من دون نافذة إطلاق مستقلة.

## بوابة القبول

- update عادي لا ينفذ `TRUNCATE` أو استيرادًا حتى مع وجود `old_data.json`.
- ترتيب الملفات الموجودة v2…v40 حتمي ومختبر (لا يوجد ملف v1 في المستودع).
- الفشل يوقف السلسلة ويحفظ آخر إصدار ناجح ويعطي exit code صحيحًا.
- الاستعادة المجربة تعيد counts والأرصدة المرجعية نفسها.

## ما نُفذ

- أعيد بناء `bin/install.php` بثلاثة أوضاع صريحة: `install` و`update` و`import-legacy`؛ التشغيل بلا وضع يرجع exit code 2 ولا يكتب شيئًا.
- أضيف `MigrationRunner` باكتشاف صارم، ومنع أرقام مكررة أو أسماء غير صالحة، وترتيب رقمي صحيح لملف `migrate_v30_container_types.php`.
- أضيف جدول `schema_migrations` وفيه الإصدار واسم الملف وSHA-256 وطريقة الاعتماد والنتيجة والمدة والوقت.
- لا يسجّل الملف الفاشل، وتتوقف السلسلة عند أول exit code غير صفري. كما يُرفض تعديل checksum أو إدخال ترحيل قديم قبل آخر إصدار مطبق.
- أضيفت معاينة `--dry-run` وفحص `--verify-only` من دون backup أو كتابة.
- نُقل الاستيراد القديم إلى `LegacyImporter` ولا يعمل لمجرد وجود الملف. يلزم الأمر المستقل والعلمان والتأكيد المطابق لاسم القاعدة.
- الاستيراد المدمّر صار transaction قابلة للتراجع، وينظف تبعيات وحدة البوالص أولًا. وتُوسم بوالص Excel كأرشيف `is_legacy=1` بمعرّف ثابت، بما يحفظ الأرقام التاريخية المكررة من دون إضعاف تفرد السجلات الحية.
- أضيف `DatabaseBackup` دون تمرير كلمة المرور في argv، وبصلاحية ملف 0600 وSHA-256، مع `--set-gtid-purged=OFF` بعد أن كشف تمرين الاستعادة تعارض GTID فعليًا.
- أضيف فاحصا `bin/verify_installer.php` و`bin/verify_restore.php`، مع override لقاعدة اختبار CLI مقيد بالبادئة `almotawakel_test_`.

## دليل بوابة القبول

- نجح تثبيت نظيف كامل على قاعدة معزولة وطبّق 39 ملفًا من v2 إلى v40.
- نجح فشل v41 مصطنع: exit غير صفري، ظهر سبب الفشل، بقي ledger عند 39، ولم تُطبع رسالة نجاح.
- رُفض اسم ترحيل تالف ورقمان مكرران، ورُفض checksum معدل لترحيل مطبق.
- نجح تمرين backup → إسقاط قاعدة الاختبار → restore، وتطابقت أعداد الجداول والترحيلات والمستخدمين والأرصدة ومجموع الأرصدة.
- نجحت معاينة الاستيراد ثم الاستيراد الفعلي: 1,728 بوليصة أرشيفية و55 رصيدًا و49 مولدًا، مع 1,542 قيمة lookup معالجة.
- بعد الاستيراد شُغّل update مرتين؛ بقيت اللقطة `[1728, 55, 4068000.00, 49, 39]` قبل وبعد بلا تغيير.
- قبل اعتماد قاعدة العمل نجح 17/17 من فاحصات المشروع. أنشأ الاعتماد النسخة:
  `storage/backups/pre-adopt-update-20260719-151323-c1ef41.sql`
  ببصمة `26fb2a903cf3cf0fd1fe372ac92d421c433e969f89d61dbad461b021adbfaaaa`، ثم سجّل 39 ترحيلًا كـ`adopted/success`.
- شُغّل update على قاعدة العمل مرتين بعد الاعتماد؛ لم توجد ترحيلات معلقة وبقي ledger متسقًا.

## الرجوع

إذا ظهر خلل لاحق متعلق بهذه المرحلة: أوقف الكتابة، واستعد نسخة `pre-adopt-update` المذكورة أعلاه. لا تعدّل ملف ترحيل مسجل؛ أنشئ رقم ترحيل جديدًا للإصلاح.
