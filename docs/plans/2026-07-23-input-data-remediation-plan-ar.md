# خطة معالجة الإدخال وسلامة البيانات — نظام المتوكل

**معرّف الخطة:** `DATA-REMEDIATION-2026-07-23`  
**تاريخ الإنشاء:** 23 يوليو 2026  
**الإصدار:** 1.0  
**الحالة العامة:** لم يبدأ التنفيذ  
**التقرير المصدر:** [تقرير تدقيق مسارات الإدخال وسلامة البيانات](../reports/2026-07-23-input-data-integrity-audit-ar.md)

تهدف الخطة إلى توحيد حماية الإدخال، منع التكرار والكتابة الجزئية، تثبيت قواعد المال في قاعدة البيانات، وإصلاح مسار الترحيلات قبل توسيع الاستخدام. التنفيذ مرتب من الاحتواء والنسخ الاحتياطي إلى التحقق، ثم المعاملات والقيود، ثم دفتر الحركة المالية والاختبارات والإطلاق.

---

## Scope

### In

- قاعدة بيانات نسخة الويب ومسار migrations.
- كل نماذج الإدخال المالية والتشغيلية.
- Validation في المتصفح والخادم وقاعدة البيانات.
- Idempotency، transactions، locking، والتزامن.
- الأذونات والحركات والمراحل والبوالص.
- الخزنة والفيزا والمديونيات والتحصيلات.
- المناديب والتسويات.
- المستندات والفواتير والكشوف.
- أدوات التحقق وCI والتوثيق.
- تنظيف الاستثناءات المكتشفة بعد نسخة احتياطية وموافقة.

### Out

- تغيير القواعد المحاسبية المعتمدة دون قرار مستقل.
- إعادة تصميم بصري شامل لا يخدم سلامة الإدخال.
- حذف الأرشيف القديم.
- تعديل بيانات العمل تلقائيًا دون dry-run وموافقة.
- استبدال النظام بتقنية أو framework جديد.

### حالات البنود

| الرمز | الحالة | المعنى |
|---|---|---|

### قواعد تحديث الوثيقة

بعد كل جلسة تنفيذ أو فحص:

1. تحديث حالة المهمة.
2. إضافة تاريخ آخر تحديث.
3. ربط commit/PR أو الملفات المعدلة.
4. تسجيل أوامر التحقق والنتيجة.
5. تسجيل أي فرق مالي قبل/بعد.
6. عدم حذف مهمة قديمة؛ تستخدم «ملغاة بقرار» مع السبب.
7. إضافة أي نتيجة جديدة إلى سجل النتائج الإضافية.

### بوابات لا يجوز تجاوزها

- نسخة احتياطية واختبار استعادة قبل migration أو تنظيف بيانات.
- لا كتابة تنظيفية قبل dry-run.
- لا تعديل migration سبق اعتمادها؛ migration جديد فقط.
- مقارنة الأرصدة والمجاميع قبل وبعد كل تغيير مالي.
- اختبار سلبي لكل validation جديد.
- اختبار double-submit لكل POST مالي مهم.
- اختبار تزامن حقيقي لكل settlement/approval.
- rollback واضح لكل مرحلة.

## 4. Action items

## المرحلة 0 — الاحتواء وإصلاح خط الأساس

### REM-000 — تجميد الترحيلات مؤقتًا

- **الأولوية:** P0.
- **الحالة:** ⬜.
- **يعالج:** `FIND-P0-001`.
- **الإجراء:** منع أي تشغيل `install/update/migrate` على قاعدة العمل حتى إتمام REM-001…005.
- **معيار القبول:** توثيق قرار التجميد وعدم وجود محاولة ترحيل غير مراجعة.

### REM-001 — إنشاء نسخة احتياطية قابلة للاستعادة

- **الأولوية:** P0.
- **الحالة:** 🟨؛ استُنسخت قاعدة محلية إلى قاعدة اختبار معزولة واختُبرت عليها
  التسوية، بينما نسخة Hostinger النهائية مطلوبة قبل التنفيذ الإنتاجي.
- **الإجراء:**
  - إنشاء dump مؤرخ مع SHA-256.
  - استعادته في قاعدة معزولة.
  - تشغيل فحوص العدد والمجاميع على الأصل والنسخة.
- **معيار القبول:** تطابق الجداول والأعداد والمجاميع المالية الأساسية.

### REM-002 — إنشاء بصمة Schema فعلية

- **الأولوية:** P0.
- **الحالة:** ✅ محليًا؛ أضيفت `schema_fingerprint.php` ببصمة مطبعة بين
  MySQL وMariaDB، ويتبقى ربطها ببوابة CI/الإنتاج.
- **الإجراء:** تصدير وصف الجداول والأعمدة والـdefaults والمفاتيح والفهارس وForeign Keys وgenerated columns وcollations وtriggers.
- **معيار القبول:** ملف مقارنة قابل للتكرار على الأصل والاختبار.

### REM-003 — مطابقة v2–v48 مع القاعدة

- **الأولوية:** P0.
- **الحالة:** ✅ على النسخة المعزولة؛ تم إثبات v2–v41 وإكمال postconditions
  v44–v48، ويبقى تشغيل نفس الخطة على نسخة Hostinger المستعادة.
- **الإجراء:** تحديد أثر كل migration وتصنيفها: مطبق، مطبق جزئيًا، غير مطبق، أو غير قابل للإثبات.
- **معيار القبول:** جدول قرار مستقل لكل إصدار.

### REM-004 — اعتماد baseline ترحيلات مراجَع

- **الأولوية:** P0.
- **الحالة:** 🟨؛ الأداة والاختبار جاهزان، والتطبيق الإنتاجي محجوب حتى backup
  Hostinger ونافذة صيانة معتمدة.
- **الإجراء:**
  - عدم تعديل checksums بلا إثبات.
  - إنشاء إجراء reconciliation لمرة واحدة يرفض التنفيذ ما لم يثبت أن الفارق
    الوحيد في v2–v41 هو حارس CLI المعروف.
  - تسجيل البصمة القديمة والجديدة والسبب والمنفذ والوقت في سجل تدقيق إضافي
    append-only قبل تحديث baseline.
  - فحص postconditions الخاصة بـv44–v48، ثم تسجيلها كإصدارات reconciled/adopted
    ببصماتها الحالية دون إعادة تنفيذها.
  - التجربة على نسخة مستعادة أولًا.
- **معيار القبول:** `install.php update --verify-only` ينجح على النسخة ثم الإنتاج.

### REM-004A — جعل مشغّل الترحيلات متوافقًا مع Hostinger

- **الأولوية:** P0.
- **الحالة:** ✅ محليًا؛ يعمل بإصدار واحد لكل عملية PHP، دون `proc_open`، مع
  advisory lock وسجل حدث بعد النجاح.
- **المشكلة المثبتة:** `MigrationRunner::runPhp()` يعتمد على `proc_open`، وهو
  معطل على Hostinger مع بقية دوال تشغيل العمليات.
- **الإجراء:** تصميم مسار CLI لا يحتاج دوال PHP المعطلة ويضمن:
  1. فحص ledger والبصمة قبل التشغيل.
  2. تشغيل إصدار واحد فقط في عملية PHP مستقلة.
  3. تسجيل النجاح بعد تحقق postconditions.
  4. ترك الإصدار غير مسجل عند الفشل.
  5. مسار recovery صريح إذا نجح DDL وفشل تسجيل ledger.
- **معيار القبول:** تجربة ترقية معزولة تحت إعداد `disable_functions` المطابق
  للإنتاج، مع نجاح المايجريشن والسجل وفشل آمن عند fault injection.

### REM-004B — منع النشر من تجاوز ledger

- **الأولوية:** P0.
- **الحالة:** ✅ محليًا؛ `deploy.sh` يرفض `--migrate` الخام ويستخدم `apply-one`
  مع backup SHA وpost-gate، ويبقى تثبيته على Hostinger جزءًا من نافذة الإصلاح.
- **الإجراء:**
  - إلغاء تشغيل `php bin/migrate_vN.php` الخام من `deploy.sh`.
  - استبداله بأمر واحد مسؤول عن الفحص والتشغيل والتسجيل والتحقق.
  - إضافة pre-deploy gate تفشل إذا اختلف أي checksum أو وُجد schema artifact
    لإصدار pending.
  - إضافة post-deploy gate تشترط صفر pending ونجاح `--verify-only`.
- **معيار القبول:** لا يمكن لعملية نشر ناجحة أن تترك schema مطبقًا بلا صف ledger.

- **الحالة:** ⬜.
- **القواعد:**
  - دعم الأرقام العربية والفارسية و`٫` و`٬`.

### REM-103 — Text and identifier rules
